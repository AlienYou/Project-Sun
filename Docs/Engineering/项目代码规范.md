# Project Sun 项目代码规范

状态：现行。版本：1.0。生效日期：2026-08-16。

## 1. 目的与适用范围

本文是 Project Sun 所有项目自有 C# 代码的统一开发规范，适用于运行时代码、编辑器工具、自动化测试以及与 Unity 资源序列化有关的代码变更。

本文规定通用代码质量和工程约束，不替代领域规范：系统权威与职责以[系统架构与开发边界](系统架构与开发边界.md)为准；射击和物理层以[战斗调试与物理层规范](战斗调试与物理层规范.md)为准；武器、附件、AI、场景和资源制作继续遵循对应 Authoring 与 Production 文档。

第三方源代码原则上保持只读。必须修改时，应先确认许可证允许并复制到 `Assets/_ProjectSun` 或项目自有代码目录，记录来源、修改原因和后续升级风险。

## 2. 基础技术约束

- Unity 固定使用 `2022.3.51f1c1`；未经专项评估和批准不得升级 Unity、URP、Input System 或其他 Package。
- 运行时代码不得依赖 `UnityEditor`。
- 不手动修改 `Library`、`Temp`、`Logs`、`obj`、自动生成的 `.csproj` 和 `.sln`。
- 不使用超出当前 Unity/C# 编译环境支持范围的语言特性。
- 新增依赖或 Package 必须说明用途、许可证、运行时成本、构建影响、维护责任和移除方案。
- 不通过关闭编译警告、忽略异常或吞掉日志来掩盖问题。

## 3. 目录、命名空间与文件

### 3.1 目录职责

| 目录 | 职责 |
| --- | --- |
| `Assets/Scripts/Core` | 通用战斗基础类型、生命、伤害和跨系统基础设施 |
| `Assets/Scripts/Input` | Input System 封装、按键映射和设置持久化 |
| `Assets/Scripts/Player` | 玩家移动、重生、观战和玩家状态适配 |
| `Assets/Scripts/Weapons` | 武器、配装、附件、ADS 数据和战术装备规则 |
| `Assets/Scripts/Rounds` | 队伍、回合、比赛规则和规则查询 |
| `Assets/Scripts/AI` | Bot、导航、感知和掩体行为 |
| `Assets/Scripts/Presentation` | 第一人称表现、相机、动画、瞄具和渲染表现 |
| `Assets/Scripts/UI` | HUD、菜单和只读状态展示 |
| `Assets/Scripts/Bootstrap` | 场景安装、依赖连接和兼容入口 |
| `Assets/Editor` | 编辑器窗口、构建器、Validator、迁移和 EditMode 测试 |

新增运行时模块应优先放入现有职责目录。只有职责长期稳定且无法合理归入现有模块时才增加一级目录。

### 3.2 命名空间

- 项目运行时代码使用 `ProjectSun.FPS.<Module>`。
- 编辑器代码使用 `ProjectSun.FPS.Editor` 或 `ProjectSun.FPS.Editor.<Module>`。
- 测试代码使用与被测模块对应的命名空间，并以 `.Tests` 结尾。
- 禁止把项目自有类型放入全局命名空间。
- 文件夹与命名空间应保持职责对应，但不要求机械复制全部目录层级。

### 3.3 文件规则

- 一个文件原则上只包含一个主要公开类型，文件名与主要类型名一致。
- 与主要类型强关联的小型私有类型可以放在同一文件；可独立复用或需要独立测试的类型应拆分。
- `.cs` 文件由 Unity 识别时必须保留对应 `.meta`；移动、重命名或删除时同步处理 `.meta`。
- 文件不得使用没有明确原因的区域折叠来隐藏过大的类型；类过大时按职责拆分。

## 4. 命名规范

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 类型、枚举、接口 | PascalCase；接口以 `I` 开头 | `RoundManager`、`IDamageable` |
| 方法、属性、事件 | PascalCase | `RestartMatch`、`TimeRemaining`、`Died` |
| 私有字段 | camelCase，不使用下划线前缀 | `playerHealth` |
| 参数和局部变量 | camelCase | `spawnPose` |
| 常量 | PascalCase | `MaxTeamSize` |
| 布尔值 | 使用 `is`、`has`、`can`、`should`、`allow` 等可判断语义 | `isReloading`、`CanEditLoadout` |
| 集合 | 使用复数或明确集合含义 | `defenderBots`、`activeEquipmentActors` |
| 尝试型方法 | 可能正常失败时使用 `Try`，返回 `bool` 并通过 `out` 返回结果 | `TryGetSpawnPose` |
| 事件处理方法 | `On` + 事件名称 | `OnPlayerDied` |
| 配置方法 | 只负责显式注入依赖时使用 `Configure` | `ConfigureCombatants` |

禁止使用无业务含义的缩写、单字母字段或 `Manager`、`Helper`、`Utils` 等无法表达职责的泛化命名。循环索引和极小数学作用域可使用 `i`、`j` 等惯例名称。

## 5. 格式与代码组织

- 使用 4 个空格缩进，不使用 Tab 表达代码层级。
- 大括号单独占行，遵循现有 Allman 风格。
- `using` 位于文件顶部；移除未使用引用。
- 类型成员按“常量与序列化字段、运行时字段、属性与事件、Unity 生命周期、公开方法、私有方法”组织。
- 相关逻辑保持邻近；不为追求固定顺序而把事件订阅与取消订阅分散到难以审查的位置。
- 优先使用提前返回降低嵌套，但不能省略必要的错误日志或状态恢复。
- 复杂条件应提取为有业务含义的方法或局部变量。
- 避免超长方法。一个方法同时承担校验、状态变更、资源创建和表现更新时，应按职责拆分。
- 不提交被注释掉的旧实现、大段调试代码或没有跟踪编号的临时分支。

格式化工具可以执行机械整理，但不得在功能提交中无关地重排第三方代码或大量未修改文件。

## 6. 注释与文档

### 6.1 注释原则

- 所有具有业务含义、状态转换、数学计算、兼容处理、性能优化或非显然行为的逻辑必须使用清晰中文注释。
- 注释说明设计意图、执行约束和边界情况，不重复代码语法。
- 简单赋值、命名完整的空值判断和明显循环不需要逐行注释。
- 修改逻辑或参数时同步更新注释；过期注释视为缺陷。
- 面向 Unity Inspector 使用者的说明统一使用中文。

### 6.2 类型与公共 API

- 新增公开类型必须说明职责、生命周期、主要调用方和失败行为。
- 公共方法使用 XML `<summary>`；所有参数使用 XML `<param>`。
- 有返回值且行为不显然时使用 `<returns>`。
- 可能返回 `null`、返回缓存对象、修改输入对象或具有线程/生命周期限制时必须明确说明。
- 公共事件说明发布时机、是否可能重复、订阅者是否需要取消订阅。

### 6.3 参数说明

所有参数都必须说明：

- 用途和业务含义。
- 单位，例如秒、米、角度、像素或归一化比例。
- 有效范围和 Clamp 行为。
- 默认行为。
- `null`、负数、零、空数组等特殊值含义。

Inspector 字段使用中文 `[Tooltip]`；具有范围约束时配合 `[Range]`、`[Min]` 或自定义校验。私有辅助方法的参数在含义、单位或特殊值不明显时也必须有中文说明。

## 7. 类型与 API 设计

- 默认使用最小可见性；只有稳定调用契约需要跨类型访问时才公开。
- 优先通过只读属性、查询方法和明确命令方法暴露状态，不直接公开可变集合或字段。
- 公共集合返回只读视图、枚举或受控副本，不能让调用方绕过规则修改内部状态。
- 配置数据与运行时状态分离；ScriptableObject 保存受控定义，不持有当前回合的易变状态。
- 规则修改与状态查询分离。HUD、动画、音频和渲染只能消费状态或事件，不能成为规则权威。
- 能正常预期失败的操作使用 `Try*`；配置损坏、必需依赖缺失等异常情况记录明确错误。
- 不用 `null` 同时表达多种业务状态；复杂结果应使用明确枚举或结果类型。
- 新增全局静态状态前必须说明生命周期、重载行为、测试隔离和清理方式。
- 不为了当前离线实现，把玩家对象、场景 Transform 或表现组件写入未来需要同步的稳定业务数据。

## 8. Unity 序列化与配置

- 序列化字段保持 `private` 并使用 `[SerializeField]`，除非存在必须公开写入的明确契约。
- 所有 Inspector 字段必须有中文 `[Tooltip]`；单位、范围、默认值和特殊值需要写清楚。
- 重命名已有序列化字段时使用 `[FormerlySerializedAs]` 保留场景、Prefab 和资产兼容。
- 删除或更改序列化字段类型前，必须检查现有场景、Prefab 和 ScriptableObject 引用并制定迁移方式。
- 必需组件使用 `[RequireComponent]`、启动校验或可定位错误约束。
- `OnValidate` 只做轻量、确定且不会破坏数据的编辑器校验；不得静默覆盖人工校准结果或执行高成本场景搜索。
- ScriptableObject 配置需要在写入目录前验证稳定 ID、数值范围、兼容关系和关键引用。
- 运行时不得直接修改共享 ScriptableObject 资产来保存玩家或回合状态。
- Prefab、场景和资产引用优先显式序列化或由 Bootstrap 注入，不依赖对象名称猜测。

## 9. 生命周期与依赖管理

- 明确区分 `Awake`、`OnEnable`、`Start`、`OnDisable` 和 `OnDestroy` 的职责。
- `Awake` 用于建立组件内部不变量和同对象依赖；`Start` 用于依赖其他对象已经完成 `Awake` 的初始化。
- 可重复启停组件的事件订阅放在 `OnEnable`，对应取消放在 `OnDisable`。
- 只在整个对象生命周期订阅一次的事件可以在 `Awake`/配置阶段订阅，但必须在 `OnDestroy` 取消。
- 配置方法重复调用时必须先解除旧依赖订阅，不能累积回调。
- 协程、临时相机、AudioListener、材质、纹理和其他运行时对象在禁用、销毁或状态切换时正确停止或释放。
- 初始化顺序需要特殊保证时，优先通过明确的 Bootstrap/Installer 调用建立，不滥用 Script Execution Order。
- 必需引用缺失时尽早失败并记录对象上下文；不得在每帧尝试搜索和修复。

## 10. 查找与引用

- Bootstrap、场景安装器或明确兼容路径可以在初始化时执行一次受控全局查找。
- `Update`、`FixedUpdate`、射击、AI 感知、渲染回调等高频路径禁止使用 `FindObjectOfType`、`FindObjectsOfType`、`GameObject.Find` 或 `Resources.Load`。
- 初始化时发现的引用应缓存并验证生命周期。
- 不依赖 Hierarchy 顺序、对象返回顺序或对象名称作为权威身份。
- 队伍、槽位、武器和配置使用稳定身份或显式引用。
- 兼容查找必须有中文注释、使用条件和迁移计划，不能成为新内容默认工作流。

## 11. 状态、事件与错误处理

### 11.1 状态修改

- 每个权威状态只有一个明确所有者。
- 状态转换由所有者提供的方法执行，并在方法内验证前置状态。
- UI 和表现层不得直接修改生命、伤害、比分、回合、配装合法性或观战目标规则。
- 重置流程必须显式覆盖相关状态，不能依赖重新加载场景隐藏泄漏。
- 多步状态修改失败时，要么不改变原状态，要么执行清晰的回滚和错误报告。

### 11.2 事件

- 事件名称表达已经发生的事实，例如 `Died`、`Changed`，不使用含糊的 `UpdateEvent`。
- 发布事件前先完成权威状态写入，使订阅者读取到一致结果。
- 必须考虑重复发布、订阅顺序、对象销毁和回合重置。
- 高频事件不得通过装箱、闭包或临时集合产生不必要分配。
- 跨系统战斗事件应使用稳定只读数据，不要求 HUD 回查场景推断攻击者或受害者。

### 11.3 错误与日志

- 必需配置缺失、数据冲突和无法继续的初始化问题使用 `Debug.LogError`，并传入相关 Unity 对象作为上下文。
- 可降级但需要制作人员处理的问题使用 `Debug.LogWarning`。
- 正常玩家操作失败不刷 Console；通过 UI 状态、返回值或开发调试界面反馈。
- 高频循环不得重复输出相同错误。应在状态变化时记录一次，或使用明确的诊断节流。
- 日志包含系统、对象和可执行的修复方向，避免只有“null”“failed”等无上下文文本。
- 不捕获宽泛异常后静默忽略。需要捕获时记录上下文，并恢复到确定状态。
- 不在日志中输出隐私数据、账号凭据、授权密钥或外部服务秘密。

## 12. 数值、时间与随机性

- 使用 `Time.deltaTime` 的帧率无关逻辑必须说明时间尺度；暂停或 UI 动画需要 `unscaledDeltaTime` 时明确标注。
- 物理状态变更放在适当的 `FixedUpdate` 或物理 API 调用路径，不混用帧时间造成不稳定结果。
- 距离统一使用 Unity 世界米，角度使用度，时间使用秒；名称或注释必须能识别单位。
- 浮点数不直接使用 `==` 判断近似结果；使用容差或 `Mathf.Approximately`，并说明业务容差。
- 除数值稳定性有明确原因外，优先使用 `float` 与 Unity API 保持一致。
- 玩法随机性需要可测试或可复现时，通过受控随机源或种子注入，不能散落调用全局随机状态。
- 除数、速率、持续时间和容量在使用前验证合法范围，避免 NaN、Infinity、负时间和除零。

## 13. 性能与内存

- 不在 `Update`、`FixedUpdate`、渲染回调、射击检测和 AI 高频循环中引入不必要堆分配。
- 高频物理查询使用 NonAlloc API 并复用缓冲区；缓冲区容量必须有上限和溢出处理策略。
- 缓存组件引用，避免高频调用 `GetComponent`、LINQ、字符串拼接或创建临时集合。
- 禁止无界增长的集合、对象、Render Texture、材质和日志缓存。
- 高频生成的弹道、命中特效、弹壳和类似对象应使用对象池；原型阶段暂未池化时必须记录适用范围和升级条件。
- 使用 `renderer.material`、运行时纹理或 Render Texture 时明确所有权，并在正确生命周期释放。
- 只在功能启用时执行额外渲染、AI 搜索和昂贵物理查询；说明更新频率与性能影响。
- 性能优化必须保留正确性和可维护性，并用 Profiler 证据证明收益；不接受无数据的复杂微优化。

## 14. 物理、伤害与战斗规则

- 弹道命中由相机中心射线确定瞄准目标，再由枪口射线验证实际物理路径。
- HUD 准星、瞄具模型和动画不得直接决定伤害结果。
- Wall、Character、First Person View 和 Ignore Raycast 等 Layer 遵循项目物理层规范。
- 射线、范围伤害和装备触发明确指定 LayerMask 与 `QueryTriggerInteraction`。
- 范围伤害和 AI 射击必须遵循遮挡与阵营规则，不能穿墙命中。
- 友军伤害、自伤和环境伤害的允许关系由规则层明确决定，不依赖表现层隐藏反馈。
- 高频命中查询避免 `GetComponentsInParent` 等潜在分配时，应先测量并在不破坏可扩展性的前提下优化。
- 战斗调试数据只用于诊断，不能成为 AI 决策、伤害或胜负输入。

## 15. 协程、异步与后台工作

- 简短的 Unity 生命周期等待、动画时序和回合计时可以使用协程。
- 每个协程必须明确由谁启动、何时取消以及对象禁用/销毁后的行为。
- 可被武器切换、死亡或回合重置打断的协程使用修订号、CancellationToken 或等效机制防止过期回调写入状态。
- 不使用 `async void`，Unity 事件入口除外；即便使用也必须处理异常和生命周期。
- Unity 对象和绝大多数 Unity API 只在主线程访问。
- 后台任务不得在项目退出、Domain Reload 或对象销毁后继续回调失效对象。
- 新引入异步框架前必须经过依赖评估，不为简单延迟额外引入 Package。

## 16. 编辑器工具

- 编辑器代码只放在 `Assets/Editor` 或 Editor-only 程序集。
- 修改场景、Prefab 或资产前检查 Play Mode、Prefab Mode 和目标有效性。
- 所有用户触发的修改支持 Undo；修改后正确标脏，并由用户显式决定保存。
- 批量处理先展示或记录准确目标；重复运行不得覆盖已经有效的人工调整。
- 校验默认只读。自动修复必须逐项、显式、可撤销，并说明改动内容。
- 工具不得直接修改第三方原始资源。
- 资产创建、移动、重命名和删除必须正确处理 `.meta` 与 GUID。
- 使用 `AssetDatabase`、Prefab API 和 Scene API 后恢复编辑器原状态，包括场景、选择、质量档和临时预览对象。
- 构建工具失败时不得遗留临时 Build Settings、质量设置、脏场景或误导性成功产物。
- EditorWindow 的核心逻辑应与界面分离，使 Validator 和数据规则可由测试直接调用。

## 17. 测试代码

- 纯数据、规则、计算和 Validator 优先使用 EditMode 测试。
- MonoBehaviour 生命周期、场景、相机、输入和多帧交互使用 PlayMode 测试或明确的人工验收。
- 测试名称使用 `被测行为_条件_预期结果` 或等价清晰结构。
- 每个测试独立创建和清理数据，不依赖执行顺序或其他测试遗留状态。
- 测试不得修改正式场景、Prefab、ProjectSettings 或玩家本地设置后不恢复。
- 临时 GameObject、ScriptableObject 和资产在 `finally`、TearDown 或对应生命周期中清理。
- 时间、随机数和外部状态尽可能可控，禁止使用无上限等待掩盖时序问题。
- 缺陷修复应增加覆盖原始复现路径和相邻边界的回归测试。
- 自动化通过不能替代视觉、音频、手感和目标机性能等必须人工判断的项目。

## 18. 兼容、迁移与废弃

- 序列化字段重命名使用 `[FormerlySerializedAs]`。
- 数据格式变化必须提供迁移或兼容读取路径，并说明旧数据何时可以停止支持。
- 兼容路径必须有明确触发条件、日志和移除计划，不能永久成为新资产默认路径。
- 公共 API 废弃优先使用 `[Obsolete]` 提供替代方式；确认全部调用方迁移后再删除。
- 删除系统、资源或字段前使用引用搜索、场景/Prefab 检查和 Validator 确认影响。
- 迁移工具先提供审计/预览，再执行修改，并支持 Undo、备份或可验证的回滚方式。

## 19. 安全与数据保护

- 禁止将密钥、令牌、账号、采购凭据或本地绝对路径硬编码进代码和资产。
- 外部输入、网络数据和未来服务器消息都视为不可信，进入权威状态前必须验证。
- 文件操作限制在明确目录，验证规范化后的绝对路径，不使用宽泛递归删除或覆盖。
- 构建和编辑器工具不把用户数据写入 `Assets`、第三方目录或 Unity 自动生成目录。
- Debug、测试作弊和自动修复能力必须有明确开发开关，不得静默进入正式玩家路径。

## 20. 代码评审清单

评审者至少检查：

### 职责与正确性

- 是否复用了现有系统，没有创建重复权威或平行状态机。
- 状态所有者、调用方、失败行为和生命周期是否明确。
- 空引用、重复调用、状态边界和回合重置是否安全。
- 是否保持弹道、队伍、回合、配装和瞄具职责契约。

### 序列化与资源

- 新字段是否有中文 Tooltip、范围、单位和默认行为。
- 字段重命名是否保留旧序列化数据。
- 场景、Prefab、ScriptableObject 与 `.meta` 是否完整。
- 是否避免直接修改第三方资源和无关用户改动。

### 生命周期与性能

- 事件订阅和取消订阅是否成对。
- 协程、相机、材质、纹理和临时对象是否清理。
- 高频路径是否产生不必要分配、搜索、日志或对象创建。
- 物理查询、LayerMask 和遮挡规则是否正确。

### API、注释与日志

- 可见性是否最小，参数和返回契约是否清楚。
- 业务逻辑、状态转换、计算和兼容处理是否有中文意图注释。
- 错误日志是否可定位、可行动且不会每帧刷屏。
- 没有注释掉的旧代码、无跟踪临时逻辑和敏感信息。

### 验证

- 是否新增或更新适当测试。
- C# 编译、Unity Console、EditMode/PlayMode 和相关场景验收是否有真实证据。
- 未完成的验证是否明确记录，没有把“未执行”写成“通过”。
- 相关工程计划、Authoring、Production 或 QA 文档是否同步。

## 21. 例外与规范变更

确有必要违反本规范时，变更必须记录：

- 违反的具体条款。
- 技术或产品原因。
- 影响范围和风险。
- 替代保障措施。

## 22. 完成定义

代码变更只有满足以下条件才能进入“已通过”：

- 实现符合系统职责和本规范。
- C# 编译通过，Unity Console 没有项目新增错误或警告。
- 与风险相称的 EditMode、PlayMode 和人工场景验收已经执行。
- 新增/修改参数、公开 API、事件和非显然逻辑具有正确中文注释。
- 序列化数据、Prefab、场景、资源引用和 `.meta` 完整。
- 性能敏感变更有验证结果，运行时资源和订阅能够正确释放。
- 文档与项目计划状态已经同步。

实现完成但缺少 Unity 运行、场景、构建或目标机证据时，状态只能是“待验收”。
