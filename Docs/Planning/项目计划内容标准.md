# Project Sun 项目计划内容标准

状态：现行。版本：1.1。生效日期：2026-08-16。

## 1. 目的

本文规定 Project Sun 项目计划类文档的层级、必备内容、状态口径和维护流程，确保产品、设计、程序、美术、音频、QA 与制作管理围绕同一目标推进。

本文回答的是“项目计划应该怎样组织和管理”，不描述具体功能的代码结构、工具实现、资源参数或测试操作。具体实现方式由 Engineering、Authoring、Production 和 QA 文档承接。

## 2. 适用范围

本标准适用于以下内容：

- 项目总体计划与产品阶段规划。
- Vertical Slice、Alpha、Beta、Release Candidate 等阶段计划。
- 版本、里程碑、迭代和跨团队工作包。
- 单项任务卡、验收记录和阶段复盘。
- 范围、优先级、依赖、风险、资源与状态变更。

日常技术说明、资源制作步骤、代码设计和单次缺陷记录不属于项目总计划，但必须能够追溯到相应里程碑或任务。

## 3. 计划体系与权威关系

项目计划采用五级结构：

| 层级 | 文档对象 | 回答的问题 | 维护频率 | 主要责任人 |
| --- | --- | --- | --- | --- |
| L0 | 产品与项目基线 | 为什么做、为谁做、成功是什么 | 产品方向变化时 | 项目负责人/产品负责人 |
| L1 | 项目路线图 | 先完成哪些阶段、各阶段形成什么能力 | 每个里程碑结束时 | 项目负责人/制作人 |
| L2 | 里程碑计划 | 本阶段必须交付什么、何时允许进入下一阶段 | 每周审查 | 制作人/各职能负责人 |
| L3 | 迭代与工作包 | 本周期由哪些可验收成果组成 | 每次迭代规划与复盘 | 模块负责人 |
| L4 | 任务卡与验收记录 | 谁在做什么、完成条件和证据是什么 | 执行过程中持续更新 | 任务负责人/验收人 |

权威顺序：

1. 产品目标和模式边界以《产品与模式基线》为准。
2. 阶段范围、优先级和完成状态以《Project Sun 工程开发计划》为准。
3. 当前执行内容以已批准的迭代计划和任务卡为准，但不得擅自扩大上级计划范围。
4. 实现与制作规范解释“如何交付”，不能自行改变产品范围和里程碑目标。
5. 验收报告记录证据和结果，不能反向把未批准内容追加为项目范围。

当不同层级冲突时，先暂停冲突项并修订上级计划，不能通过下级任务卡默默改变项目方向。

### 3.1 验收截图归档约束

当任务卡、验收用例或 QA 清单要求截图，或测试结果必须依靠画面状态证明时，截图必须归档到该验收报告对应的仓库内证据目录：`Docs/QA/Evidence/<任务编号>/`。验收报告必须在对应测试用例的“证据/缺陷”位置以 Markdown 图片直接展示该截图；只记录文件路径、外部链接、聊天附件或口头结论均不构成完整证据。

截图文件名使用 `<用例ID>_<步骤或内容>_<日期时间>.<扩展名>`；图片应保留足够的窗口、状态和版本上下文。仅在用例明确不需要截图且其他证据可完整证明结果时，才可省略图片，并在报告中写明原因。视频、构建产物和大体积日志仍可保存于受控外部目录，但报告必须记录其路径、摘要和与用例的对应关系。

## 4. 项目总体计划的必备内容

项目总体计划必须包含以下章节；缺失内容需要明确标记“待决策”，不能直接省略。

### 4.1 项目定义

- 产品类型、目标平台、目标用户和核心体验。
- 当前商业目标与本阶段验证目的。
- 项目成功标准和明确失败条件。
- 已确认范围、明确不做以及需要后续立项的内容。

项目定义必须稳定、简洁，不能把功能列表当作产品目标。

### 4.2 当前基线

- 当前可运行版本能够完成的玩家流程。
- 已具备的生产、测试和构建能力。
- 已验证、待验证和仅实现三种状态必须分开描述。
- 已知技术债、内容债、质量风险和外部依赖。
- 基线对应的日期、版本或提交标识。

“已有代码”“已有资源”和“已经可交付”不是同一状态。没有运行证据的内容不能写成已完成。

### 4.3 阶段路线图

每个阶段必须说明：

- 阶段目标：完成后项目获得的能力。
- 玩家价值：该阶段改善的核心体验。
- 交付边界：必须完成和明确排除的内容。
- 入口条件：开始本阶段前必须具备的条件。
- 出口条件：进入下一阶段前必须通过的质量门禁。
- 关键依赖：团队、资源、技术和外部服务依赖。
- 主要风险：最可能影响范围、时间或质量的问题。

路线图优先描述成果和能力，不罗列低层实现类名或字段。

### 4.4 里程碑与质量门禁

每个里程碑必须是可演示、可验证、可决定是否继续投入的项目状态。里程碑至少包含：

- 唯一编号和名称。
- 业务或玩家体验目标。
- 必须交付的成果集合。
- 跨职能参与范围。
- 验收负责人和决策负责人。
- 可量化的放行条件。
- 未通过时的处理方式。

里程碑不能仅以“代码完成”“资源导入完成”或日期到达作为完成标准。

### 4.5 资源与产能假设

- 团队角色、可投入人数和关键岗位缺口。
- 外包、采购、许可证和平台支持需求。
- 关键设备、目标机和测试环境。
- 人员并行限制和关键路径岗位。
- 计划所依据的工作日、假期与缓冲假设。

在人员和工期尚未确定时，计划使用依赖顺序与相对规模，不虚构精确日期。

### 4.6 风险与决策

总体计划必须维护主要风险和待决策事项：

| 字段 | 要求 |
| --- | --- |
| 风险/决策编号 | 稳定且唯一，例如 `RISK-001`、`DEC-001` |
| 描述 | 清楚说明可能发生什么或需要决定什么 |
| 影响 | 对范围、时间、成本、质量或团队的影响 |
| 概率/紧迫度 | 高、中、低或明确决策期限 |
| 负责人 | 负责推动缓解或取得决策的人 |
| 应对 | 规避、降低、转移、接受或需要的决策方案 |
| 触发条件 | 何时升级、降级或执行备用方案 |
| 状态 | 开放、监控中、已缓解、已发生、已关闭 |

高风险没有负责人和应对措施时，不得开始依赖它的里程碑。

## 5. 里程碑计划标准

里程碑计划用于把路线图转换为跨职能交付，不直接替代任务卡。

每份里程碑计划必须包含：

1. 里程碑编号、名称、目标和负责人。
2. 入口条件与计划开始窗口。
3. 玩家体验、玩法系统、内容、表现、工具、QA 和发布工程各自的交付成果。
4. 工作包清单、依赖关系和关键路径。
5. 资源假设与容量限制。
6. 风险、待决策项和外部依赖。
7. 演示范围、验收方式和出口条件。
8. 计划变更记录和最终复盘链接。

### 5.1 跨职能交付矩阵

复杂里程碑应使用交付矩阵确保没有只交玩法代码、未交内容和质量保障的情况：

| 维度 | 计划必须回答 |
| --- | --- |
| 产品/设计 | 玩家规则、体验目标和取舍是否明确 |
| Gameplay | 核心交互和规则是否闭环 |
| AI | 是否支持目标人数、地图和玩法节奏 |
| UI/UX | 玩家是否能理解状态、反馈和结果 |
| 美术/动画/VFX | 是否达到本阶段目标质量并有合法资源 |
| 音频 | 关键行为是否有可读的声音反馈 |
| 工具/生产 | 内容能否稳定、重复地制作和验证 |
| QA | 自动化、人工回归、性能和兼容性如何覆盖 |
| 构建/发布 | 是否能生成、追溯和分发本阶段产物 |

不适用的维度需要说明原因，不能留空。

## 6. 迭代与工作包标准

迭代是固定审查周期内的一组可演示成果；工作包是可由一个主要责任角色管理、可独立验收的成果集合。

### 6.1 迭代计划必须包含

- 迭代目标，只允许一个主要目标和少量支撑目标。
- 对应里程碑和质量门禁。
- 承诺工作包与候选工作包；候选项不计入承诺完成率。
- 团队容量和不可用时间。
- 关键依赖、阻塞和风险。
- 迭代演示内容与验收人。
- 中途变更规则和未完成项处理方式。

### 6.2 工作包必须满足

- 能产生可观察的项目成果，而不是无边界的“优化”或“继续完善”。
- 有单一主要负责人和明确协作角色。
- 有输入、输出、依赖、非范围和验收条件。
- 能拆成若干任务卡，并在一个里程碑内完成。
- 规模过大、跨越多个质量门禁时必须继续拆分。

## 7. 任务卡内容标准

任务卡是执行层文档，必须保持面向成果，不写成实现者的逐行操作手册。

每张任务卡必须包含：

| 字段 | 内容要求 |
| --- | --- |
| 编号与名称 | 稳定编号；名称表达交付成果 |
| 所属目标 | 对应里程碑、工作包和玩家/生产价值 |
| 优先级 | 使用统一优先级并说明理由 |
| 负责人 | 唯一主责人与必要协作者 |
| 前置依赖 | 开始前必须满足的条件 |
| 范围 | 本卡承诺交付的结果 |
| 非范围 | 明确本卡不处理的相邻内容 |
| 交付物 | 代码、资源、文档、工具、报告或构建等可检查产物 |
| 验收标准 | 可观察、可判断通过或失败的条件 |
| 验收方式 | 自动测试、人工检查、演示或数据报告 |
| 风险 | 可能影响完成的事项与升级条件 |
| 状态与记录 | 当前状态、日期、阻塞、结果和验收人 |

### 7.1 Definition of Ready

任务进入“可开始”前必须满足：

- 目标、范围和非范围明确。
- 关键设计决策已经确认，或被明确列为任务的一部分。
- 前置依赖已满足，没有未知的外部授权。
- 验收标准可执行，所需环境和资产可获得。
- 负责人理解工作量、风险和需要协作的角色。

不满足 Ready 的任务保留在需求整理状态，不进入迭代承诺。

### 7.2 Definition of Done

任务完成至少要求：

- 范围内交付物完整并可定位。
- 相关自动化和人工验收通过。
- 没有未处理的阻断级或严重缺陷。
- 性能、兼容性、许可证和资源引用符合当前阶段要求。
- 相关计划、制作规范和验收文档同步更新。
- 验收人已经记录结论；“开发完成、待验收”不等于完成。

## 8. 统一优先级

| 优先级 | 定义 | 处理原则 |
| --- | --- | --- |
| P0 | 阻断当前核心流程、构建、数据安全或里程碑签字 | 优先处理，不解决则不得放行 |
| P1 | 当前里程碑必须具备的重要体验或生产能力 | 在阶段出口前完成 |
| P2 | 显著改善质量、效率或内容规模，但可在有记录的情况下延期 | 根据容量和风险安排 |
| P3 | 探索、便利性或远期储备 | 不进入当前承诺，除非明确批准 |

优先级表示项目影响，不表示实现难度。所有 P0/P1 必须能追溯到当前里程碑目标。

## 9. 统一状态

| 状态 | 定义 |
| --- | --- |
| 需求整理 | 目标或验收尚不完整，未达到 Ready |
| 可开始 | 已满足 Ready，等待排入迭代 |
| 进行中 | 负责人已经开始执行 |
| 阻塞 | 因明确依赖无法继续，已记录责任人和解除条件 |
| 待验收 | 交付实现完成，但尚未获得全部验收证据 |
| 已通过 | 完成定义全部满足并已签字 |
| 已取消 | 经批准不再实施，保留原因和影响记录 |

“完成”“实现完成”“测试通过”和“已发布”必须区分。项目汇总只把“已通过”计入完成量。

## 10. 估算、排期与缓冲

- 优先使用小、中、大或团队统一的相对点数进行早期估算。
- 有稳定历史速度和明确人员投入后，才承诺具体日期。
- 排期必须包含依赖等待、集成、验收、缺陷修复和构建时间，不能只计算开发时间。
- 关键路径必须有明确负责人和风险缓冲。
- 探索性工作使用时间盒，到期输出结论、原型或停止建议，不能无限延长。
- 外部采购、授权、平台审核和第三方交付单独设置缓冲，不与内部实现混为一体。
- 为赶日期删减内容时，应优先调整范围并重新批准，不能静默降低完成定义。

## 11. 依赖管理

依赖必须区分：

- 内部顺序依赖：同一系统或团队前后关系。
- 跨职能依赖：程序、设计、美术、音频、QA 或发布之间的交付关系。
- 外部依赖：第三方资源、许可证、平台、服务商、设备和审批。
- 决策依赖：没有产品或技术决策便无法安全推进的事项。

每条关键依赖需要记录提供方、接收方、需要日期、当前状态和失败备用方案。只有写“依赖某团队”而没有明确交付物，不构成可管理依赖。

## 12. 变更控制

以下变化必须更新项目计划并留下记录：

- 产品目标、核心规则或目标平台变化。
- 里程碑范围、优先级、出口条件或计划顺序变化。
- 新增 P0/P1 工作，或移除已经承诺的 P0/P1 工作。
- 关键人员、外部依赖、许可证或技术方案发生重大变化。
- 风险已经发生并影响阶段目标。

变更记录至少包含：日期、发起人、原因、影响、批准人、调整内容和需要同步的文档。紧急变更可以先处理风险，但必须在最近一次项目审查时补录。

## 13. 项目审查与汇报

### 13.1 迭代审查

- 展示实际可运行成果，不用完成百分比代替演示。
- 对照承诺项逐一给出已通过、待验收、阻塞或未完成。
- 记录缺陷、风险变化、范围变化和下一迭代输入。
- 未完成工作重新评估，不自动滚入下一迭代。

### 13.2 里程碑审查

- 核对入口条件、出口条件和跨职能交付矩阵。
- 审查质量、性能、内容、许可证、构建与玩家体验证据。
- 明确作出通过、有条件通过、返工或停止四种决策之一。
- “有条件通过”必须列出条件、责任人和截止窗口，不得无限保留。

### 13.3 项目状态报告

状态报告保持简洁，至少包含：

- 当前阶段与总体健康度。
- 本周期已经通过的成果。
- 下一周期的主要目标。
- 关键路径、阻塞、风险和待决策事项。
- 范围、排期或资源变化。
- 需要管理层或跨团队协助的具体问题。

健康度使用绿、黄、红：绿色表示按当前计划可达成；黄色表示存在风险但有可行缓解方案；红色表示当前目标、时间或质量至少一项无法维持，需要决策。

## 14. 复盘与历史保留

每个里程碑结束后必须记录：

- 原目标与实际结果。
- 已交付、延期、取消和新增内容。
- 计划偏差及根因。
- 质量、生产效率和团队协作问题。
- 应保留、停止和改进的做法。
- 对后续估算、规范和路线图的调整。

失效计划不直接删除，应迁入 `Docs/Archive` 并注明被替代原因和现行文档链接。历史计划只用于追溯，不再作为当前执行依据。

## 15. 文档维护责任

| 文档 | 主责 | 必须参与审查的角色 |
| --- | --- | --- |
| 产品与模式基线 | 产品负责人 | 项目负责人、设计负责人 |
| 项目工程开发计划 | 项目负责人/制作人 | 各职能负责人、QA |
| 里程碑计划 | 制作人 | 产品、技术、美术、QA 负责人 |
| 迭代计划 | 模块负责人 | 执行人员、依赖方、验收人 |
| 任务卡 | 任务负责人 | 模块负责人、验收人 |
| 验收报告 | QA 或指定验收人 | 任务负责人、相关职能负责人 |

任何人都可以提出计划变更，但只有对应层级责任人可以批准并修改权威状态。


## 17. 本项目当前应用

当前《Project Sun 工程开发计划》承担 L1 路线图和当前阶段门禁职责；《迭代 A 任务卡》承担 L3/L4 的首个执行切片职责。后续应逐步将较大的 Gate 拆为独立里程碑计划，将跨职能成果拆为工作包，再生成任务卡，避免项目总计划继续膨胀为实现清单。

计划质量以“是否能帮助团队做取舍、识别依赖、判断完成和控制变更”为标准，不以文档篇幅或任务数量衡量。
